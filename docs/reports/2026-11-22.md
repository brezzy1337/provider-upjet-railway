# 2026-11-22

_Part of the [Phase 2 review](phase-2-review.md)._

_Environment: GitHub Codespace on Alpine 3.23, 2 vCPU, 8 GB, no Docker; `sudo` available, which is
what made the root-path test below possible._

## Summary

B2 from the Phase 1 review: the control-plane image now starts as root only long enough to take
ownership of the platform-mounted volume, then re-execs the supervisor as an unprivileged uid.
The `RAILWAY_RUN_UID=0` workaround is gone from code and docs.

| PR | Merge | What |
|----|-------|------|
| [#6](https://github.com/brezzy1337/provider-upjet-railway/pull/6) | `9e2c845` | `drop_privileges_if_root` as the supervisor's first step, `su-exec` in the image with `USER` removed, `CP_STAY_ROOT` opt-out, `RAILWAY_RUN_UID` gone from code and docs; mechanics in the state-root section of [Architecture](../architecture/control-plane.md). Harness: `CP_RUN_UID` defaults to the checkout owner when run as root; `verify` asserts no process runs as uid 0 (22 checks) |

## Verified

Native harness on 2026-11-22. The state root was first chowned to `root:root` mode 755 to imitate
a Railway mount; root runs use `sudo -E env PATH="$PATH" hack/native-cluster.sh up`.

| Scenario | Result |
|----------|--------|
| Started as root on the root-owned state root, `CP_RUN_UID` left to the harness default | 18 s to provider ready; chown of `state/` and `home/` logged; afterwards everything owned `1000:1000`, state root mode 700; **every process including the supervisor runs as uid 1000**; **22/22** |
| Mixed ownership: top directory 1000, one file in `pki/` chowned back to root | the mismatch scan triggers the chown; `ca.key` owned by 1000 afterwards; identity check passes; 22/22 |
| Healthy tree, started as root | 13 s; **no chown**; 22/22 |
| `CP_RUN_UID=0` | refused in the first lines, exit 1, no re-exec loop |
| `CP_STATE_DIR=/usr/local`, `/`, or equal to `CP_HOME`, as root | each refused before any filesystem change; `/usr/local` still root-owned |
| Unprivileged restart on that state | 10 s; no root-path log lines; 22/22 |
| Started as root with `CP_STAY_ROOT=true` | boots as root with the warning line |

No leftover processes after any scenario. Not verified: the Docker image build and Railway.

## Decided

- A tree is chowned recursively only when a `find` sees a mismatched owner or group in it, so mixed
  ownership left by an earlier root-run boot is repaired without paying for a chown on every boot.
- `su-exec` rather than `setpriv` or `gosu`: it is a 10 KB Alpine package and preserves the
  environment, which the re-exec relies on.
- `HOME` is set to `CP_HOME` for the unprivileged process so nothing tries to write under `/root`.

## Found

All found by the five-lens review of the first draft and fixed before merge:

- `CP_RUN_UID=0` re-exec'd forever: still root after `su-exec 0:0`, so the root phase ran again.
  Now refused, along with gid 0 and non-numeric values, and a sentinel makes a second pass fatal.
- Root-phase `mkdir` of the ephemeral directories left them `root:root 0700` whenever the parent was
  already correctly owned. The root phase now creates only what it chowns.
- The owner test looked at the top directory only, so root-owned files inside a correctly owned
  tree were missed. Replaced by a mismatch scan.
- The layout guard ran after the drop, so `CP_STATE_DIR=/` would have been chowned as root first.
  Path and layout validation now precede any root-time filesystem change.
- A root harness run would have dropped to uid 65532, which cannot read the checkout. The harness
  now defaults `CP_RUN_UID` to the checkout owner.

## Decided

- Secretbox over aescbc (authenticated); a KMS provider is out of scope without a KMS.
- Two certificate classes rather than one: the exported admin cert is short-lived; the in-container
  identities are minted every boot and never exported. One class could not serve both the human
  (short) and the long-running container (must not expire under it).
- Secret reads by the in-container identities are excluded from the audit log; everything a human
  does to a Secret, and every write by anyone, is logged.

## Found

- Lowering `CP_CLIENT_CERT_DAYS` did not shorten an existing longer certificate (the first suite
  issued a 400-day cert that then outlived the 90-day policy). Fixed: a cert is reused only if it
  has at least half the policy left and does not outlive the policy.
- A transient `pgrep` count of three processes right after shutdown turned out to be teardown in
  progress; a recount after 10 s is zero. Nothing to fix.
- Review (architecture, blocking): the in-container clients shared the exported 90-day `admin.crt`,
  renewed only at boot, so a container up past day 90 would have lost its own credentials. Fixed by
  splitting identities (`admin-internal`, `controller-manager` minted every boot) plus an hourly
  watchdog. The watchdog path itself is not exercised by any test.
- Review (architecture): a failed Secret list during re-encryption was hidden and the stamp moved
  anyway; the audit policy was written in a subshell so a failure would have started the API server
  without audit. Both fail closed now.
- Review (security): the key format check would have let a crafted value inject YAML into the
  EncryptionConfiguration; the key stayed in every component's environment; a disabled token's file
  lingered on the volume. All fixed.

## Decided

- `unset` only, as B3 does for the encryption key, not a re-exec of the supervisor with the token on
  a pipe; the residual and the condition under which it must be closed (a second uid) are in the
  Secrets section of Architecture, and the harness pins it with a positive control.
- Server-side apply for the Secret, so the data is not stored a second time in the
  last-applied-configuration annotation (client-side apply would do that).
- A character-set check, not a format check: Railway tokens are UUID-shaped today, but what the
  hand-built JSON needs is `[A-Za-z0-9-]`, and an upstream format change would not lock us out.
- The verify probes read the token from the environment inside single-quoted scripts, so running
  the checks does not itself put the value into `ps`.

## Found

- The first draft of the Secret-contents probe lacked its closing `]` and failed against a correct
  Secret; fixed before the first full run.
- Go's `exec.Command` keeps `argv[0]` as given, so terraform appears in `ps` as `terraform init`,
  not under the harness path. The environ check now walks each component's descendants as well.
- With an unusable token, the provider's observe fails with `Instance cannot be destroyed:
  ... lifecycle.prevent_destroy set`, not with "Not Authorized": the refresh finds nothing and the
  plan wants to destroy. Confusing but outside this change; worth a line in the authentication docs
  later.
- Review (architecture, security): the first draft stripped interior whitespace too, so `abc 123`
  would have been accepted as `abc123`. Now only leading and trailing whitespace is dropped and
  interior whitespace is refused.
- Review (security): client-side `kubectl apply` stored the token a second time in the
  last-applied-configuration annotation, and kubectl's stderr on a failed write could have echoed
  the object. Server-side apply, legacy annotation removed, diagnostics masked.
- Review (architecture, security): the environ probe found processes by path, so it could not see
  terraform (`argv[0]` is `terraform`), skipped the supervisor by construction and passed vacuously
  on an unreadable environ. It now walks the supervisor's descendants, fails closed, and a positive
  control asserts the supervisor's residual copy.
- Review (factual, consistency): the probes compared against the raw `RAILWAY_TOKEN` while `up`
  trims it; `verify` now trims and exports it the same way. The Design section's Secrets paragraph
  now points at the mechanics.
- The GC probe fails when `verify` runs twice within seconds (its namespace is still terminating).
  Pre-existing and not investigated further; a re-run passes.
- `hack/dev-cluster.sh`, the local kind helper, still builds its Secret with `--from-literal`. Out
  of B4's scope (the control-plane image).

## Session 4 (2026-11-22): B5, etcd quota, snapshots, memory

_Same environment as above._

## Summary

B5 from the Phase 1 review. etcd's quota is sized to the volume (`auto`: half of it, at most 2 GiB)
and checked at boot; a background maintenance pass defragments when fragmented and snapshots to the
volume, at boot, every six hours and on `SIGUSR1`; a NOSPACE alarm is polled for every minute and
recovered from; every Go component gets a `GOMEMLIMIT` that is its share of the container's memory
limit. The alarm scenario found two defects in the first draft and the review found three more in
the maintenance machinery; all fixed before merge.

No leftover processes after any shutdown (recounted after 10 s). Not verified: the Docker image
build, Railway, a cgroup-limited container (only the explicit-limit and no-limit paths ran), the
`etcdutl snapshot restore` procedure end to end, the 6-hour default interval as such (a 10 s interval
exercised the same periodic path), behaviour under real memory pressure (GOMEMLIMIT is set, not
stressed), and a `SIGTERM` arriving during a background pass.

## Decided

- Compaction stays the API server's job in normal operation; the pass compacts only when an alarm
  is active, because that is precisely when the API server cannot.
- The pass runs in the background after boot, one at a time, and is written so that nothing in it
  can take the supervisor down; the boot pass stays synchronous because the API server must not
  start on a database that still needs repair.
- An alarm that survives the boot pass is fatal, with the two ways out in the message. The tested
  alternative, booting on so objects can be deleted, cannot work: `crossplane core init` needs
  writes.
- `auto` quota (half the volume, at most 2 GiB) rather than a fixed 2 GiB, so a small Railway volume
  boots instead of crash-looping; an explicit value must fit.
- Fixed percentage shares for `GOMEMLIMIT`, overridable per component, with the total checked at
  boot; measured sizing waits for a real cgroup-limited run.

## Found

- The alarm scenario found two defects by running, not by reading: the API server cannot compact
  under NOSPACE, and the old readiness gate wedged on an alarmed member. Both would have made a full
  etcd on Railway unrecoverable without a shell.
- Review (security, architecture, factual; blocking): the first pass ran under `set -euo pipefail`
  with plain `$(...)` assignments over `etcdctl | grep` pipelines, so an empty or late reply would
  have killed the supervisor, the opposite of "never fatal". Every helper is now total, the pass is
  always invoked under `||`, and a stubbed run proves the shell survives.
- Review (architecture; blocking): the pass ran synchronously in the supervise loop, so a hung etcd
  (etcdctl retries a refused connection until its command timeout) would have blocked `SIGTERM`
  handling and death detection for minutes. Background job now; shutdown stops it first.
- Review (security): `alarm disarm` would have cleared a `CORRUPT` alarm too; now NOSPACE only.
  Pruning used `ls` word-splitting and ran after the save; now an array, pruned to KEEP-1 first,
  and `KEEP=0` means none.
- Review (architecture): a boot snapshot on every restart would let a crash loop rotate every good
  snapshot away; the boot pass now keeps a snapshot under an hour old. Defrag needs a copy's worth of
  free space and stalls etcd; it now runs only when fragmented or alarmed and when the space is
  there. Small Railway volumes would have crash-looped on the fixed 2 GiB quota; `auto`.
- Review (factual, consistency): the no-token, no-limit verify count was stated as 29; it is 34.
- The snapshot directory was created world-readable despite `umask 077` (a default ACL on the
  checkout wins); chmod 700 explicitly.
- Running `verify` twice within seconds fails the GC probe (its namespace is still terminating); a
  re-run passes. Pre-existing.

## Open

etcd client authentication (the B3 leftover), then the first Railway deploy and the
composition-function spike. The restore procedure in Architecture should be exercised once against a
real snapshot before it is relied on, and the first run under a real cgroup limit should check the
`GOMEMLIMIT` shares against observed usage.

  store; checked by a harness probe with `admin-internal`.
- Peer TLS too, with the same server certificate and `--peer-client-cert-auth`, after the security
  review showed the peer port was a second unauthenticated door (it serves `/members` and accepts
  raft from a spoofed member id). The member's recorded peer URL is updated at boot because the
  `--initial-*` flags are read only when the data directory is created.
- One signing helper for every certificate, writing through temp names: the review found that a
  crash between a key write and its certificate write would have wedged every later boot, and that
  the original code had three copies of the same openssl sequence.
- Stated in the docs rather than oversold: in the single-uid container every process can read the
  client key files and the etcd CA key, so this closes the network path and enables a uid split; the
  split itself needs per-component key ownership, an untraversable PKI directory and a reduced RBAC
  identity for the provider.

## Found

- Review (architecture, security): the CA guard tested only the key file and no certificate pair was
  checked for a torn write; both fixed by `ensure_ca`, `sign_cert` and `keypair_ok`, which also cover
  the cluster CA, the front-proxy CA and the API server's serving certificate.
- Review (security): the harness refusal checks accepted any failure, a timeout included, and the
  alarm check passed vacuously when `etcdctl` failed. The probes now assert the cause (curl's TLS
  alert, or a closed connection with no HTTP reply) after a positive control, and the alarm check
  fails on an `etcdctl` error.
- Review (redundancy, factual, consistency): the new helper had been inserted between an existing
  doc comment and its function; counts for the other verify modes were missing; wording in two
  places overstated how closed the peer port was. All fixed.
- curl negotiates HTTP/2 by ALPN and etcd's peer port does not speak it; the harness probe uses
  `--http1.1`.

## Open

The first Railway deploy, then the composition-function spike. After that, the uid split for the
provider and terraform, which this change makes possible. Still unexercised: `etcdutl snapshot
restore` end to end, and a run under a real cgroup limit.
