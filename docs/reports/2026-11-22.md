# 2026-11-22

_Environment: GitHub Codespace on Alpine 3.23, 2 vCPU, 8 GB, no Docker; `sudo` available, which is
what made the root-path test below possible._

## Summary

B2 from the Phase 1 review: the control-plane image now starts as root only long enough to take
ownership of the platform-mounted volume, then re-execs the supervisor as an unprivileged uid.
The `RAILWAY_RUN_UID=0` workaround is gone from code and docs.

## Shipped

| PR | Merge | What |
|----|-------|------|
| [#6](https://github.com/brezzy1337/provider-upjet-railway/pull/6) | `9e2c845` | `drop_privileges_if_root` as the supervisor's first step, `su-exec` in the image with `USER` removed, `CP_STAY_ROOT` opt-out, `RAILWAY_RUN_UID` gone from code and docs; mechanics in the state-root section of [Architecture](../architecture/control-plane.md). Harness: `CP_RUN_UID` defaults to the checkout owner when run as root; `verify` asserts no process runs as uid 0 (22 checks) |

## Verified

Native harness on 2026-11-22. The state root was first chowned to `root:root` mode 755 to imitate
a Railway mount; root runs use `sudo -E env PATH="$PATH" hack/native-cluster.sh up`.

| Scenario | Result |
|----------|--------|
| Started as root on the root-owned state root, `CP_RUN_UID` left to the harness default | 18 s to provider ready; chown of `state/` and `home/` logged; afterwards everything owned `1000:1000`, state root mode 700; **every process including the supervisor runs as uid 1000**; **22/22** |
| Mixed ownership: top directory 1000, one file in `pki/` chowned back to root | the mismatch scan triggers the chown; `ca.key` owned by 1000 afterwards; identity check passes; 22/22 |
| Healthy tree, started as root | 13 s; **no chown**; 22/22 |
| `CP_RUN_UID=0` | refused in the first lines, exit 1, no re-exec loop |
| `CP_STATE_DIR=/usr/local`, `/`, or equal to `CP_HOME`, as root | each refused before any filesystem change; `/usr/local` still root-owned |
| Unprivileged restart on that state | 10 s; no root-path log lines; 22/22 |
| Started as root with `CP_STAY_ROOT=true` | boots as root with the warning line |

No leftover processes after any scenario. Not verified: the Docker image build and Railway.

## Decided

- A tree is chowned recursively only when a `find` sees a mismatched owner or group in it, so mixed
  ownership left by an earlier root-run boot is repaired without paying for a chown on every boot.
- `su-exec` rather than `setpriv` or `gosu`: it is a 10 KB Alpine package and preserves the
  environment, which the re-exec relies on.
- `HOME` is set to `CP_HOME` for the unprivileged process so nothing tries to write under `/root`.

## Found

All found by the five-lens review of the first draft and fixed before merge:

- `CP_RUN_UID=0` re-exec'd forever: still root after `su-exec 0:0`, so the root phase ran again.
  Now refused, along with gid 0 and non-numeric values, and a sentinel makes a second pass fatal.
- Root-phase `mkdir` of the ephemeral directories left them `root:root 0700` whenever the parent was
  already correctly owned. The root phase now creates only what it chowns.
- The owner test looked at the top directory only, so root-owned files inside a correctly owned
  tree were missed. Replaced by a mismatch scan.
- The layout guard ran after the drop, so `CP_STATE_DIR=/` would have been chowned as root first.
  Path and layout validation now precede any root-time filesystem change.
- A root harness run would have dropped to uid 65532, which cannot read the checkout. The harness
  now defaults `CP_RUN_UID` to the checkout owner.

## Session 2 (2026-11-22): B3, secrets at rest, audit, credential lifetimes

_Same environment as above._

## Summary

B3 from the Phase 1 review. Secrets are encrypted in etcd with a key that comes from the environment
and, when supplied externally, never touches the volume, the API server writes an audit log, admin credentials live 90 days
instead of ten years, and the static bearer token is off in the image.

## Shipped

| PR | Merge | What |
|----|-------|------|
| [#7](https://github.com/brezzy1337/provider-upjet-railway/pull/7) | `118bf73` | `CP_ENCRYPTION_KEY` secretbox encryption with a fingerprint stamp and rotation via `CP_ENCRYPTION_KEY_PREVIOUS`; audit policy and JSON log; `CP_CLIENT_CERT_DAYS` 90 with midpoint renewal, serving cert 365; `CP_ADMIN_TOKEN_ENABLED` (false in the image); six new verify checks (28); mechanics in the Secrets, audit and credential lifetimes section of [Architecture](../architecture/control-plane.md) |

## Verified

Native harness on 2026-11-22, two suites (12 boots). `KA`/`KB` are two `openssl rand -base64 32` keys.

| Scenario | Result |
|----------|--------|
| Cold boot with `CP_ENCRYPTION_KEY=KA` | 17 s; a probe Secret is stored in etcd as `k8s:enc:secretbox:v1:`; `state/ENCRYPTION` holds the key fingerprint; the audit log has the Secret write at `Metadata` with no request body and no internal-identity Secret reads; exported admin cert 89 days, in-container identity `control-plane-internal` separate; no component carries the key in its environment; TLS 1.2 accepted, 1.1 refused; **28/28** |
| Restart with `KA` | exported `admin.crt` unchanged, in-container certs re-minted; 28/28 |
| Restart with `KA` and `CP_CLIENT_CERT_DAYS=400`, then back to 90 | exported cert reissued each way (399, then 89 days left); a further same-policy restart reissues nothing |
| Restart with `KB` only | refused: `Secrets in etcd were encrypted with key <fpA>, but CP_ENCRYPTION_KEY has fingerprint <fpB>`; exit 1 |
| Key with an injected YAML line appended | refused: must be exactly the base64 of 32 bytes |
| `CP_ENCRYPTION_KEY_PREVIOUS` equal to the key | treated as no rotation |
| Rotate: `KB` with `CP_ENCRYPTION_KEY_PREVIOUS=KA` | "rotating" logged; the existing Secrets re-encrypted one by one; stamp moves to `fpB`; the Crossplane TLS Secret still readable; 28/28 |
| Restart with `KB` only | boots; 28/28 |
| `CP_REQUIRE_EXTERNAL_KEY=true` with no key | refused with the `openssl rand -base64 32` instruction |
| `CP_ADMIN_TOKEN_ENABLED=false` | no token kubeconfig written; `pki/tokens.csv` removed; a request with the old token gets HTTP 401 |
| `CP_AUDIT_LOG_PATH=-` | boots; audit events appear in the API server's own log |
| Fresh state, no key, harness mode | key generated under `pki/` with the warning; 27/27 |

No leftover processes after any shutdown (recounted after 10 s). Not verified: the Docker image build
and Railway.

## Decided

- Secretbox over aescbc (authenticated); a KMS provider is out of scope without a KMS.
- Two certificate classes rather than one: the exported admin cert is short-lived; the in-container
  identities are minted every boot and never exported. One class could not serve both the human
  (short) and the long-running container (must not expire under it).
- Secret reads by the in-container identities are excluded from the audit log; everything a human
  does to a Secret, and every write by anyone, is logged.

## Found

- Lowering `CP_CLIENT_CERT_DAYS` did not shorten an existing longer certificate (the first suite
  issued a 400-day cert that then outlived the 90-day policy). Fixed: a cert is reused only if it
  has at least half the policy left and does not outlive the policy.
- A transient `pgrep` count of three processes right after shutdown turned out to be teardown in
  progress; a recount after 10 s is zero. Nothing to fix.
- Review (architecture, blocking): the in-container clients shared the exported 90-day `admin.crt`,
  renewed only at boot, so a container up past day 90 would have lost its own credentials. Fixed by
  splitting identities (`admin-internal`, `controller-manager` minted every boot) plus an hourly
  watchdog. The watchdog path itself is not exercised by any test.
- Review (architecture): a failed Secret list during re-encryption was hidden and the stamp moved
  anyway; the audit policy was written in a subshell so a failure would have started the API server
  without audit. Both fail closed now.
- Review (security): the key format check would have let a crafted value inject YAML into the
  EncryptionConfiguration; the key stayed in every component's environment; a disabled token's file
  lingered on the volume. All fixed.

## Session 3 (2026-11-22): B4, the Railway token

_Same environment as above._

## Summary

B4 from the Phase 1 review. `RAILWAY_TOKEN` is read once before any component starts, checked
against `[A-Za-z0-9-]`, and removed from the environment; the `railway-creds` Secret is built from
kubectl's stdin instead of a command line; the token is never logged. Terraform processes forked by
the provider were inspected while running and carry no token.

## Shipped

| PR | Merge | What |
|----|-------|------|
| [#8](https://github.com/brezzy1337/provider-upjet-railway/pull/8) | this PR | `take_railway_token` right after the privilege drop: whitespace stripped, character set enforced, `unset` before the first `start_bg`; `write_railway_credentials` takes the value as an argument and feeds `kubectl create secret --from-file=credentials=/dev/stdin`; the unset-token warning kept. Harness: five new verify checks (33 with `RAILWAY_TOKEN` set for `verify`, 29 plus a SKIP line without); mechanics in the Secrets, audit and credential lifetimes section of [Architecture](../architecture/control-plane.md) |

## Verified

Native harness on 2026-11-22, key `KA`, fake token `fake-token-for-b4-test` (the provider cannot
authenticate with it, which does not matter for what is tested). Token and key were read from files
so that neither ever appeared on a command line, the probe's own included.

| Scenario | Result |
|----------|--------|
| Cold boot with `KA` and the token | 38 s to provider ready; `railway-creds` decodes to exactly `{"token":"fake-token-for-b4-test"}`; `ProviderConfig/default` references it; none of etcd, kube-apiserver, kube-controller-manager, crossplane or the provider has `RAILWAY_TOKEN` in `/proc/<pid>/environ`; the value is on no process command line and in no file under `log/`, audit log included; the supervisor's stderr does not contain it; **33/33** |
| Negative control | the same environ probe run against the supervisor's own pid flags it (bash's `unset` leaves the exec-time copy), so the check can see a leak when there is one |
| Live terraform run (a `Project` object reconciled with the fake token) | `terraform init` and `terraform apply -refresh-only` captured while running: 0 of 86 environment variables are `RAILWAY_TOKEN` |
| Restart with the token padded with spaces and a newline | 15 s; Secret identical to the clean JSON; cluster identity unchanged; 33/33 |
| Token containing `"`, `\`, `;` or a JSON fragment | each refused with `FATAL: RAILWAY_TOKEN contains characters outside [A-Za-z0-9-]`, exit 1, nothing started, the value absent from the log; a plane already running was not disturbed |
| Restart with the token unset | 12 s; WARNING logged; Secret and ProviderConfig from the earlier boot still present and intact; `verify` without `RAILWAY_TOKEN` prints one SKIP line, 29/29 |
| Started as root on a root-owned state root with the token (the B2 path) | chown logged, every process uid 1000, the token survived the `su-exec` re-exec and the Secret was written; 16 s; 33/33 |

No leftover processes after any shutdown (recounted after 10 s). Not verified: the Docker image
build and Railway.

## Decided

- `unset` only, as B3 does for the encryption key, rather than a re-exec of the supervisor with the
  token handed over on a pipe. The one copy that remains is the supervisor's own exec-time
  environment block, and in a container where every process shares one uid and the cluster-admin
  kubeconfig, it grants nothing that is not already had. Documented rather than engineered away.
- A character-set check, not a format check: Railway tokens are UUID-shaped today, but what the
  hand-built JSON needs is `[A-Za-z0-9-]`, and an upstream format change would not lock us out.
- The verify probes read the token from the environment inside single-quoted scripts, so running
  the checks does not itself put the value into `ps`.

## Found

- The first draft of the Secret-contents probe lacked its closing `]` and failed against a correct
  Secret; fixed before the first full run.
- Go's `exec.Command` keeps `argv[0]` as given, so terraform appears in `ps` as `terraform init`,
  not under the harness path. The environ check now walks each component's descendants as well.
- With an unusable token, the provider's observe fails with `Instance cannot be destroyed:
  ... lifecycle.prevent_destroy set`, not with "Not Authorized": the refresh finds nothing and the
  plan wants to destroy. Confusing but outside this change; worth a line in the authentication docs
  later.
