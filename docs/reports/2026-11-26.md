## Decided

- One `Workload` XRD with a `preset` field and one Composition per preset, rather than one XRD per
  workload: one kind to learn, one status to read, a new option is a new Composition. A thin
  `HermesAgent` wrapper that composes a `Workload` stays possible later.
- Every preset renders to provider-helm `Release` and provider-kubernetes `Object`, targeted through
  a per-cluster `ProviderConfig` made from the `KubernetesCluster`'s connection Secret.
- Custom presets ship with guardrails from the start: Composition-written namespaces, a CEL deny
  list, and a reduced-RBAC kubeconfig per workload when needed.
- Order inside Phase 3 is fixed by dependency: functions, cluster, workload, write-back, more clouds.

## Found

- Crossplane 2.x composite resources are namespaced and used directly; claims exist only for legacy
  cluster-scoped XRDs. The first draft of the plan said "claim-able, namespaced", which is a
  contradiction in 2.x; the plan now says namespaced composite resource, no claim, with the
  Composition picked through `spec.crossplane.compositionSelector`.
- The Hermes mount path, port and image in the plan come from the Hermes Docker guidance and have
  not been run here; the preset spike confirms them.

### Decided

- Composition functions run as supervised processes, like the provider, and are registered by hand:
  a paused `Function` plus a paused `FunctionRevision/<name>-local`, with `status.endpoint` and
  `status.capabilities` patched through the status subresource. Under the External package runtime
  nothing else writes those fields, and the Deployment runtime, which does, has nothing to schedule.
- The placeholder image string is `supervised.local/control-plane/<name>:process`, in both
  `Function.spec.package` and `FunctionRevision.spec.image`; the CRD demands an image shape and the
  paused reconcilers never fetch it.
- Functions start after Crossplane core (step 6, after `crossplane core start` in step 5), not
  before it as first written: Crossplane must own metrics port 8080 before the functions' SDK tries
  to bind it, and a dial Crossplane attempts before a function is up is an ordinary reconcile error
  it retries. Reverse shutdown stops the functions before Crossplane, which costs Crossplane a few
  failed dials while it is itself stopping.
- The harness keeps `CP_CROSSPLANE_METRICS_PORT` at 8080 (8080 must be free on the host) so it
  reproduces the collision instead of hiding it, and asserts who owns the port.
- 3% `GOMEMLIMIT` per function, total 91 with two; a function idles at a few tens of MiB (the RSS
  above).
- The drain window is 70 s (7 components x `CP_SHUTDOWN_TIMEOUT` 10 s); the live service was set,
  the runbook says 70.
- The fixture stays a harness fixture under `hack/fixtures/functions-spike/`, group
  `harness.railway.crossplane.io`, not a product API; the product XRDs come with items 2 and 3.
- From the review: the start order stays as it is rather than moving Crossplane's metrics off 8080,
  which the architecture lens proposed. With Crossplane elsewhere the first function would bind its
  SDK metrics on all interfaces, unauthenticated; with the order, every function stays loopback-only,
  and an SDK that made the lost bind fatal would fail the mTLS readiness gate, so a bump cannot pass
  silently. The `--metrics-address` upstream patch stays the clean long-term fix (see
  [Architecture](../architecture/control-plane.md#composition-functions)).
- From the review: the borrowed root CA key is deleted as soon as the certificates are signed
  (every process shares one uid, so a copy on disk was readable by all of them for the container's
  life); registrations carry a supervisor label and stale ones are pruned at boot; `GOMEMLIMIT`
  treats every `CP_FUNCTIONS` name as a function; the function clones are pinned by commit as well
  as tag; and the default harness round trip is hermetic (a `ConfigMap`), with the Railway `Project`
  path opt-in, because the fake token had been reaching the real API (see Found).

### Found

- **The functions' SDK squats Crossplane's metrics port.** function-sdk-go v0.7.1 (`Serve` in
  `sdk.go`) starts a Prometheus metrics server on `DefaultMetricsAddress = ":8080"` in every
  function, on all interfaces, with no flag or environment variable in either function's CLI to
  move or disable it, and it ignores a failed bind (`_ = metricsServer.ListenAndServe() // Ignore
  errors`). Crossplane core's metrics port defaults to 8080 and it refuses to start when the port
  is taken. With the functions started first, the first Railway deploy (`f9cc19bd`) crash-looped
  on `failed to start metrics server: failed to create listener: listen tcp :8080: bind: address
  already in use`. The harness had not seen it because it shifted Crossplane's metrics to 18080,
  so the first function took :8080 locally without consequence: a blind spot, now closed by keeping
  8080 and checking who answers there. Fix in the start-order commit: Crossplane starts first and
  owns 8080, the functions' bind fails silently, and each function listens on loopback only.
- The `Function` CRD's CEL rule requires `spec.package` to look like `registry/repository:tag`; the
  first registration with `local://<name>` was refused at boot.
- The namespaced `Project` is served at `railway.m.crossplane.io/v1alpha1`, not `v1beta1`; a first
  fixture draft said `v1beta1` and failed with "no matches for kind Project". `ClusterProviderConfig`
  is at `v1beta1`.
- The namespaced managed resources default their `providerConfigRef` to `kind: ClusterProviderConfig,
  name: default`, which did not exist: the supervisor only wrote the legacy `ProviderConfig/default`.
  It now writes both.
- Under TLS 1.3 a rejected client certificate arrives as an alert after a successful-looking
  handshake, so `openssl s_client` reports `Verify return code: 0 (ok)` with or without a valid
  client certificate; the readiness gate and the harness also require `ALPN protocol: h2` and the
  absence of any `SSL alert`, and the harness requires the server's HTTP/2 SETTINGS frame.
- Both functions' `go.mod` require Go 1.26.11, above the image's 1.26.7 pin, and the build stages set
  `GOTOOLCHAIN=local`, which refuses to download a newer toolchain; the pin moved to 1.26.11. A
  function version bump needs the same check (and the SDK check under Open).
- Removing a name from `CP_FUNCTIONS` left its `Function` and `FunctionRevision` behind: no owner
  reference, and the paused reconcilers never notice. Worse than litter, as the review pointed out:
  ports are positional, so the stale revision's `status.endpoint` would point at another function's
  port and misroute a pipeline silently. Fixed in the review commit with the supervisor label and the
  boot-time prune.
- The `implementer` agent definition merged in PR #19 strips the Bash tool (its `disallowedTools`
  patterns), so both review-fix slices (code and docs) were written without a shell and verified by
  the central thread; a follow-up PR replaces the deny list with an allowlist.
- `kubectl get functions` shows the registered functions without `INSTALLED` or `HEALTHY`, because the
  reconcilers that set those columns are paused. Cosmetic, documented.
- With the fake token, the composed `Project` still reached `Ready=True` with a UUID external name;
  Terraform reported only "unknown value for workspace_id after apply", and deleting the XR removed it.
  The project never appeared in the account's project list, and the Terraform provider did send the
  fake bearer token (the generated `main.tf.json` held it). The inference, labelled as such and
  not verified beyond this run, is that Railway's API creates an unowned temporary project for an
  unauthenticated request, as the CLI once did for logged-out users. Two consequences: the harness
  round trip touches the real Railway API even with the fake token, and the `SKIP` branch written
  for an auth failure was not exercised. The fixture README, which had said the fake token yields a
  SKIP, is corrected in this PR: it says the `Project` path talks to the real Railway API and
  carries the temporary-project inference, labelled as such. The review fixes then made that path
  opt-in (`VERIFY_LIVE_RAILWAY=1`) behind a hermetic `ConfigMap` default.

### Open

- A function version bump must re-check two things, and nothing automates either: the new tag's
  `go.mod` against the image's Go pin, and the SDK's metrics default, since an SDK that made the
  failed bind on `:8080` fatal would fail the boot at the readiness gate (loudly, not silently). The
  clean alternative is a small upstream patch adding `--metrics-address` to the functions, carried
  like `hack/upstream/`.
- The follow-up PR that replaces the `implementer` agent's `disallowedTools` deny list with an
  allowlist, so implementers can run their own verification again.
- Supply chain, the rest of the image: commit pins for the `crossplane-build` and `tfprovider-build`
  stages, which still clone by tag alone, and checksums for the fetched Kubernetes, etcd and
  Terraform binaries.
- The 7-day cooldown on the two function tags: on 2026-11-26 both were 2 days old. The rule in
  `CLAUDE.md` makes a sub-7-day pin a human decision; if it is taken at merge, the user takes it and
  the decision is recorded here by the next session.
- `.claude/handoff/phase-3-functions-spike.md` still names `XRailwayProject` as an example of the
  fixture; historical, left as written.
- What the opt-in `SKIP` branch should key on if Railway does not answer an unauthenticated request
