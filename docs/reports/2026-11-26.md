## Decided

- One `Workload` XRD with a `preset` field and one Composition per preset, rather than one XRD per
  workload: one kind to learn, one status to read, a new option is a new Composition. A thin
  `HermesAgent` wrapper that composes a `Workload` stays possible later.
- Every preset renders to provider-helm `Release` and provider-kubernetes `Object`, targeted through
  a per-cluster `ProviderConfig` made from the `KubernetesCluster`'s connection Secret.
- Custom presets ship with guardrails from the start: Composition-written namespaces, a CEL deny
  list, and a reduced-RBAC kubeconfig per workload when needed.
- Order inside Phase 3 is fixed by dependency: functions, cluster, workload, write-back, more clouds.

## Found

- Crossplane 2.x composite resources are namespaced and used directly; claims exist only for legacy
  cluster-scoped XRDs. The first draft of the plan said "claim-able, namespaced", which is a
  contradiction in 2.x; the plan now says namespaced composite resource, no claim, with the
  Composition picked through `spec.crossplane.compositionSelector`.
- The Hermes mount path, port and image in the plan come from the Hermes Docker guidance and have
  not been run here; the preset spike confirms them.
