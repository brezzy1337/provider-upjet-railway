passed over the internet through the TCP proxy. Two things had to change on the way, both found by
the deploy rather than by review: Railway's Dockerfile validator rejects BuildKit cache mounts

its 2026-10-21 incident contain underscores, which the B4 character set written for UUID tokens
refused (PR #14). A Phase 1 deployment from 2026-08-27 was found still running in the account and
its project was reused.

## Decided

- Reuse the existing project and service rather than create `crossplane-control-plane` as the runbook
  said, wiping the Phase 1 data; a second project would have doubled the bill. The runbook keeps its
  greenfield commands and notes what was done instead.
- Drop the BuildKit cache mounts rather than give them Railway's `s/<service id>-<path>` id, which
  would pin the Dockerfile to one deployer's service and cannot go in a template.
- Widen the B4 set to `[A-Za-z0-9._-]` and keep it a character-set check; the supervisor comment now
  states the JSON-safety invariant (no quote, backslash, whitespace or control character) apart from
  the width Railway's tokens need, so the two are not conflated again. No boot-time validation of the
  token against Railway's API (correlated failure, hand-written client; the `ProviderConfig` surfaces
  it anyway).
- The authentication page owns the token-format history; other pages link to it.

## Found

- Railway exposes the memory limit through cgroup v2; `CP_MEMORY_LIMIT_BYTES` is not needed there.
- Railway's Dockerfile validator rejects cache mounts without an id and the `VOLUME` instruction.
- Railway's tokens are not UUIDs any more; the 2026-11-22 report's "an upstream format change would
  not lock us out" was wrong, because the set had been narrowed to the format seen.
- A volume mount-path change triggers a rebuild from the stored code snapshot, and a failed
  replacement still removes the running deployment. A variable set or deleted by the CLI without
  `--skip-deploys`, or edited in the dashboard, did not redeploy by itself in this session.
- Railway stops the old container before starting the new one on redeploy; about 14 s of API
  downtime counted from the start of the old shutdown; never two containers on the volume.
- `railway ssh`, `railway service files` and `railway volume files` all need a registered SSH key,
  and the SSH shell receives every service variable, sealed ones included, in its environment.
- Deployment status `SUCCESS` means the container started; a crash loop keeps it.
- The serving certificate was reissued on the redeploy although the SAN set had the same members.
  With `CP_APISERVER_CERT_SANS` removed, the proxy hostname moved from the explicit list to the
  appended position, so the likely cause is an order-sensitive comparison; one observation, the code
  not re-read to confirm. Harmless (same CA), not fixed.
- An etcd maintenance pass "by signal" ran at 19:52:31 during an SSH session; nothing in the session
  sent `SIGUSR1` knowingly. Not explained, harmless.
- The Phase 1 container had been billing since 2026-08-27 while the docs and the session notes
  treated the first deploy as not yet done.
