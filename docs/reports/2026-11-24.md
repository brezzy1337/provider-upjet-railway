## Decided

- The platform configures the endpoint: no deployer-supplied SAN or external URL, since Railway
  tells the service its own proxy hostname and port at runtime. A template therefore needs only two
  secrets from the person deploying it.
- Railway's Infrastructure as Code is not adopted yet: it needs Node.js for its SDK and does not yet
  cover the TCP proxy or the Dockerfile path, and `railway.json` is deprecated with a December cutoff.
  The runbook uses plain CLI commands, which cover everything.
- The first deploy uploads the working tree (`railway up`) and connects the GitHub source afterwards,
  so the GitHub app installation is not on the critical path of the first boot.

## Found

- Railway's SIGTERM-to-SIGKILL window defaults to 0 s. Without `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`
  every redeploy would kill etcd mid-shutdown; the supervisor now warns and the runbook sets 60.
- The exported kubeconfig used `CP_APISERVER_PORT` for its URL even when a proxy sits in front, so
  on Railway it would have pointed at the wrong port unless `CP_EXTERNAL_URL` was set by hand. The
  proxy port now flows in from the platform.
- Installing a downloaded binary into `PATH` is refused by this session's safety policy; the CLI
  install and the device-code login are the person's steps.
